## Зачем эта работа

В ЛР8 заявки хранились в памяти процесса C# и терялись после его остановки. В ЛР9 вы сохраняли их в PostgreSQL с помощью SQL. Сегодня сервер сохраняет данные в те же таблицы через EF Core. Проверка одна: создали заявку, выключили API, включили — заявка на месте.

Файл `schema.sql` не отменяет эту работу. Он использовался для изучения SQL. Стандартный подход EF Core — **миграция**: набор изменений схемы, который приводит базу данных в соответствие с моделью кода.

### EF Core простыми словами

**Entity Framework Core** — объектно-реляционный преобразователь (ORM), который отображает объекты C# на таблицы и формирует SQL. Вы пишете на C# «найди заявки со статусом New». Он преобразует выражение в SQL и выполняет запрос в PostgreSQL.

```csharp
tickets.Where(t => t.Status == "New")
```

в уме должно звучать:

```sql
SELECT * FROM tickets WHERE status = 'New';
```

Если вы не можете объяснить соответствующий SQL, значит работа с ORM выполняется без понимания сформированного запроса; соответствие LINQ и SQL проверяется на защите. В отчёт положите одну такую пару «строка C# / тот же смысл SQL из ЛР9».

**DbContext** описывает наборы сущностей (`DbSet`) и использует настроенное подключение к PostgreSQL.

### Что такое миграция

Вы изменили класс: добавили поле. Миграция — файл с SQL «добавь столбец». Команды:

```bash
cd backend
dotnet ef migrations add InitialCreate
dotnet ef database update
```

Первая команда создаёт файлы в папке Migrations. Вторая применяет их к указанной базе данных.

Правила:

- сменили модель — новая миграция, не ручное редактирование ранее применённой миграции;
- не изменять учебную схему вручную в pgAdmin вместо миграции; просмотр для диагностики допустим;
- `schema.sql` оставить как справку, не как замену `database update`.

### Пароль

В `appsettings.json` часто кладут строку вида `Host=localhost;Password=секрет`. Если файл в Git — секрет утечёт. Сделайте так:

- пароль в [user-secrets](https://learn.microsoft.com/ru-ru/aspnet/core/security/app-secrets) или в переменной окружения;
- либо локальный файл, который перечислен в `.gitignore`;
- в репозитории пример `appsettings.Development.json.example` **без** пароля.

Проверка перед сдачей:

```bash
git grep -i password
```

Не должно найти ваш настоящий пароль.

### Как проверить, что данные сохраняются в PostgreSQL, а не в списке в памяти

1. В Swagger создать заявку, записать `id`.
2. В терминале остановить API (`Ctrl+C`).
3. Снова `dotnet run`.
4. `GET` по этому `id` — та же тема и статус.

Пусто на шаге 4: либо сервис всё ещё пишет в `List<>`, либо строка подключения смотрит в другую базу, чем вы открыли в pgAdmin.

Если человеческий номер повторился — ответ **409**, а не необработанная ошибка 500.

Раздатка EF с пары: раздатку с пары (её выдаёт преподаватель).

### Пример: куда класть строку подключения

```bash
# в папке backend, не коммитить результат
dotnet user-secrets init
dotnet user-secrets set "ConnectionStrings:Default" "Host=localhost;Port=5432;Database=course_tickets;Username=…;Password=…"
```

В `appsettings.json` — только имя ключа или пустой пример. В Git — `appsettings.Development.json` без пароля или в `.gitignore`.

## Сдача

Рестарт не стирает заявку. Нет id — 404. Миграции в Git, пароля нет. На защите: чем миграция не `schema.sql`; где лежит пароль; какой SQL соответствует вашему `.Where`.

## Частые ошибки

- `database update` не запускали — API завершается ошибкой из-за отсутствующих таблиц.
- Две базы: писали в `tickets_dev`, смотрели `postgres`.
- Оставили `List<Ticket>` без необходимости и удивляетесь рестарту.
- Закоммитили пароль, потом «удалили в новом коммите» — в истории он остался. Скажите преподавателю, секрет смените.
- Миграции не добавили в Git — у соседа `database update` нечего применять.
- Смешали ручной `schema.sql` и миграции без согласования имён таблиц.
