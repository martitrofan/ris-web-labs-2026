## Зачем эта работа

В ЛР8 заявки жили в списке C# и умирали вместе с процессом. В ЛР9 вы научились хранить их в PostgreSQL руками. Сегодня сервер **сам** пишет в те же таблицы. Проверка одна: создали заявку, выключили API, включили — заявка на месте.

Файл `schema.sql` не отменяет эту работу. Он был учебником. Боевой способ для C# — **миграция**: снимок «какой SQL выполнить, чтобы база совпала с кодом».

## Цель

Тот же API, что в ЛР8, но память процесса больше не источник правды.

## Что сдать

- пакеты EF Core и Npgsql (мост C# ↔ PostgreSQL);
- класс `DbContext` — «какие таблицы видит программа»;
- папка миграций **в Git**;
- POST, оба GET, оба PATCH работают как раньше;
- нет строки → 404;
- строка подключения (хост, пароль) **не** в Git.

JSON и коды ЛР8 не менять. Клиент Vue сегодня можно не трогать.

## Теория на пару

40 минут.

### EF Core простыми словами

**Entity Framework Core** — переводчик. Вы пишете на C# «найди заявки со статусом New». Он превращает это в SQL и ходит в PostgreSQL.

```csharp
tickets.Where(t => t.Status == "New")
```

в уме должно звучать:

```sql
SELECT * FROM tickets WHERE status = 'New';
```

Если не можете сказать SQL вслух — вы копируете магию, на экзамене это вскроется. В отчёт положите одну такую пару «строка C# / тот же смысл SQL из ЛР9».

**DbContext** — оглавление: вот сущность Ticket, вот Sites, вот строка «как дозвониться до базы».

### Что такое миграция

Вы изменили класс: добавили поле. Миграция — файл с SQL «добавь столбец». Команды:

```bash
cd backend
dotnet ef migrations add InitialCreate
dotnet ef database update
```

Первая команда создаёт файлы в папке Migrations. Вторая применяет их к живой базе.

Правила:

- сменили модель — новая миграция, не правка старой «на глаз»;
- не чинить учебную базу руками в pgAdmin вместо миграции (для отладки глянуть — можно);
- `schema.sql` оставить как справку, не как замену `database update`.

### Пароль

В `appsettings.json` часто кладут строку вида `Host=localhost;Password=секрет`. Если файл в Git — секрет утечёт. Сделайте так:

- пароль в [user-secrets](https://learn.microsoft.com/ru-ru/aspnet/core/security/app-secrets) или в переменной окружения;
- либо локальный файл, который перечислен в `.gitignore`;
- в репозитории пример `appsettings.Development.json.example` **без** пароля.

Проверка перед сдачей:

```bash
git grep -i password
```

Не должно найти ваш настоящий пароль.

### Как понять, что пишете не в старый список

1. В Swagger создать заявку, записать `id`.
2. В терминале остановить API (`Ctrl+C`).
3. Снова `dotnet run`.
4. `GET` по этому `id` — та же тема и статус.

Пусто на шаге 4: либо сервис всё ещё пишет в `List<>`, либо строка подключения смотрит в другую базу, чем вы открыли в pgAdmin.

Если человеческий номер повторился — ответ **409**, не жёлтый 500.

Раздатка EF с пары: раздатку с пары (её выдаёт преподаватель).

### Пример: куда класть строку подключения

```bash
# в папке backend, не коммитить результат
dotnet user-secrets init
dotnet user-secrets set "ConnectionStrings:Default" "Host=localhost;Port=5432;Database=course_tickets;Username=…;Password=…"
```

В `appsettings.json` — только имя ключа или пустой пример. В Git — `appsettings.Development.json` без пароля или в `.gitignore`.

## Порядок на 4 часа

1. Поставить пакеты и глобальный инструмент `dotnet-ef`, если его нет (`dotnet ef` должен отвечать).
2. Классы сущностей один в один со столбцами ЛР9 (имена C# можно `SiteId`, в базе `site_id` — это нормально, настраивается).
3. Убрать пароль из отслеживаемых файлов.
4. Миграция и `database update`. Открыть pgAdmin: таблицы появились. Если не похожи на `/db/schema.sql` — таблица соответствия имён в отчёте.
5. Сервис ЛР8: вместо списка вызвать `DbContext`. Контроллер почти не трогать.
6. Сценарий рестарта, скрин или лог в отчёт.
7. Пара LINQ / SQL в отчёт.

## Сдача

Рестарт не стирает заявку. Нет id — 404. Миграции в Git, пароля нет. На защите: чем миграция не `schema.sql`; где лежит пароль; какой SQL прячется за вашим `.Where`.

## Частые ошибки

- `database update` не запускали — API падает на отсутствии таблиц.
- Две базы: писали в `tickets_dev`, смотрели `postgres`.
- Оставили `List<Ticket>` «на всякий случай» и удивляетесь рестарту.
- Закоммитили пароль, потом «удалили в новом коммите» — в истории он остался. Скажите преподавателю, секрет смените.
- Миграции не добавили в Git — у соседа `database update` нечего применять.
- Смешали ручной `schema.sql` и миграции без согласования имён таблиц.
