## Что получится к концу

Один репозиторий на весь семестр:

```text
ваш-репозиторий/
├── README.md          ← ФИО, группа, пока можно без темы
└── .gitignore         ← GitHub предложит при создании; не удаляйте
```

Папок `docs/`, `frontend/`, `backend/` пока нет — их заведёте в **этом же** репозитории на ЛР1 и дальше.

Проверка:

1. Ссылка открывается **у преподавателя** (не только у вас).
2. В истории есть хотя бы один коммит.
3. В `README.md` есть ФИО и группа.
4. Если репозиторий **приватный** — преподаватель в Collaborators и принял приглашение.

**Не делайте:** тринадцать репозиториев «на каждую лабу», пустой репозиторий без README, ссылку, которую видите только вы.

## 1. Для чего нужна система контроля версий

**Система контроля версий (СКВ)** — программа, которая помнит *все сохранённые версии* ваших файлов и *кто что менял*. На курсе это **Git**.

Без Git бывает так:

- файл `работа_финал3_точно.docx` на Рабочем столе;
- флешка одногруппника со «вчерашней» копией;
- «у меня дома работало, сюда не скопировал».

С Git:

- каждое осмысленное сохранение — **коммит** (снимок);
- можно откатиться, если сломали код;
- преподаватель видит *что* сдано *когда*, а не архив с почты;
- замечание пишется к конкретной версии, а не «в том файле, который вы присылали в сентябре».

**GitHub** — это не Git. Git работает на вашем компьютере. GitHub — сайт, где лежит **удаленная копия** того же репозитория, issues и доступ для преподавателя. Аналоги сайта: GitLab, Codeberg (см. раздел 7).

Коротко:

| Слово | Что это |
|-------|---------|
| Git | программа контроля версий на диске |
| репозиторий | папка проекта + история коммитов |
| коммит | снимок выбранных файлов с комментарием |
| remote / origin | адрес копии в интернете |
| push | отправить коммиты на GitHub |
| pull | забрать чужие коммиты к себе |
| clone | скачать репозиторий целиком |
| issue | тикет: замечание, задача, вопрос в репозитории |

## 2. Как создать репозиторий

Нужен аккаунт на [github.com](https://github.com). Почта должна открываться: GitHub шлёт письма с приглашениями и уведомлениями об issue.

### На сайте GitHub (так проще всего)

1. Войдите. Справа сверху **«+» → New repository** (Создать репозиторий).
2. **Repository name.** Латиницей, коротко, по теме курса, например `ris-web-2026`. Не `untitled` и не чужое имя из туториала.
3. **Description** можно пропустить.
4. **Private** (приватный) — **включите**. Так работу не гуглят однокурсники и боты. Как раздать доступ преподавателю — отдельный раздел ниже.
5. Поставьте галочку **Add a README file**.
6. **Add .gitignore** → шаблон **VisualStudio** или **Node** (оба нормальны на старте; позже дополните).
7. **Create repository**.

Готово: у вас есть адрес вида `https://github.com/ВАШ-ЛОГИН/ris-web-2026`.

### С компьютера (если папка уже есть)

В PowerShell в папке проекта:

```powershell
git init
git add README.md
git commit -m "ЛР0: старт репозитория"
git branch -M main
git remote add origin https://github.com/ВАШ-ЛОГИН/ris-web-2026.git
git push -u origin main
```

Саму пустую оболочку на GitHub всё равно создайте через сайт (без второго README, если файлы уже локально).

**Один репозиторий на семестр.** ЛР1–13 — новые папки и коммиты *внутри него*, не новые репозитории.

## 3. Как делать коммиты

Коммит — не «сохранить в Word». Это точка в истории: *какие файлы* и *зачем*.

Правило курса: после осмысленного куска работы (README, ТЗ, экран, API) — коммит и **push**. Пока коммит только на вашем диске, преподаватель его не видит.

### Через GitHub Desktop (если командная строка пугает)

1. Установите [GitHub Desktop](https://desktop.github.com).
2. **File → Clone repository** — скачать свой репозиторий.
3. Меняйте файлы в Cursor / VS Code / блокноте.
4. Слева список изменённых файлов. Краткий **Summary** (например `ЛР1: заявка на тему`).
5. **Commit to main**, затем **Push origin**.

### Через терминал

```powershell
git status                 # что изменилось
git add README.md          # или: git add -A   (все файлы, осторожно)
git commit -m "ЛР0: ФИО и группа в README"
git push
```

Сообщение коммита — по-русски или по-английски, но **по делу**: `ЛР2: схема ER` лучше, чем `asdf` и `правки`.

### Частые ошибки

| Ошибка | Как правильно |
|--------|----------------|
| Правили файлы, забыли `push` | После коммита всегда `git push` |
| Один коммит «вся сессия» на 400 файлов | Дробите: документы / клиент / сервер |
| В Git попали `bin/`, `node_modules/`, пароли | `.gitignore`; секреты не коммитить никогда |
| `commit` без `add` | Git коммитит только то, что в индексе |
| Репозиторий создали, README пустой | ФИО и группа в первом коммите |

В Git **не кладут:** `.env`, строку подключения к PostgreSQL, пароли, zip чужого проекта, личные фото.

## 4. Что такое issue

**Issue** — запись в репозитории: задача, вопрос или замечание преподавателя. Это не чат в Telegram и не комментарий к оценке в журнале.

На курсе issue — основной канал сдачи замечаний:

- «ЛР1: доработать — нет ФИО в README»;
- «ЛР2: нет абзаца про 3НФ»;
- «ЛР3: нужны три экрана в `/frontend`».

У issue есть номер (`#1`, `#2`), статус **Open** / **Closed**, обсуждение комментариями.

Преподаватель **не** пишет в личку разбор каждого файла. Он открывает репозиторий и заводит issue. Если репозиторий приватный и вас нет в Collaborators — issue вы не получите, а статус в таблице будет «недоступен».

## 5. Как работать с issue

### Студент

1. Включите уведомления GitHub (почта или колокольчик на сайте).
2. Откройте **Issues** в своём репозитории. Прочитайте текст целиком.
3. Исправьте файлы → коммит → **push**.
4. В том же issue напишите комментарий: что сделали (и в каком коммите, если удобно).
5. **Не закрывайте** issue преподавателя сами, пока он не написал, что доработка принята. Закрытие — сигнал «замечание снято».

Пример ответа:

> Исправил README: добавил ФИО и группу. Коммит `a1b2c3d`.

### Если issue про ЛР, которую вы уже переделали

Напишите это в комментарии. Не создавайте второй репозиторий «чтобы было чисто».

### Преподаватель (чтобы вы понимали процесс)

1. Смотрит чеклист методички.
2. Если чеклист не закрыт — открывает issue с формулировкой «что не так».
3. Если доработка на месте — комментарий «доработка принята» и issue **закрывают**.

Ваша работа «сдана», когда файлы в Git проходят чеклист, а некогда открытые замечания по этой ЛР закрыты.

## 6. Приватный репозиторий и приглашение преподавателя

Это обязательный блок. Без доступа преподавателя работа **не проверяется**.

На курсе нормальный вариант — **приватный** репозиторий + приглашение. Публичный тоже откроется по ссылке, но тогда любой в интернете видит ваш код и ТЗ. Приватный без приглашения для преподавателя выглядит как **404** — в таблице это статус «недоступен».

Аккаунт преподавателя на GitHub: **`martitrofan`**.

### Сделать репозиторий приватным

Если при создании уже выбрали Private — этот шаг пропускаете.

1. Откройте репозиторий → **Settings** (Настройки).
2. Внизу блок **Danger Zone**.
3. **Change repository visibility** → **Make private**.
4. Подтвердите имя репозитория.

Владелец всегда видит свой приватный репозиторий. Другие — только после приглашения.

### Пригласить преподавателя (GitHub)

1. **Settings → Collaborators** (иногда **Collaborators and teams**).
2. **Add people**.
3. Введите **`martitrofan`** (логин, не ФИО).
4. Роль для личного репозитория: collaborator с правом **Write** — достаточно, чтобы преподаватель открывал файлы и писал issue. Не выдавайте **Admin**, если не хотите, чтобы репозиторий могли удалить.
5. **Add XXX to this repository**.
6. GitHub шлёт приглашение. Пока преподаватель его **не принял**, доступа нет.

Проверка с вашей стороны: в Collaborators видна строка `martitrofan` со статусом принятого приглашения, не «pending» неделями. Если pending висит — напишите преподавателю: письмо GitHub могло уйти в спам.

Ссылку на репозиторий всё равно отправьте через **форму курса** (главная сайта лабораторных). Форма не заменяет приглашение: в форму пишут URL, приглашение даёт *вход*.

### Если репозиторий на GitLab

1. **Settings → General → Visibility** → **Private**.
2. **Manage → Members → Invite members**.
3. Логин или почта преподавателя — как сказали на паре (на GitHub это `martitrofan`).
4. Роль не ниже **Reporter** (видеть код и issues). Надёжнее **Developer**.
5. Отправьте приглашение и дождитесь принятия.

## 7. Ключевые команды и инструменты

### Что поставить

| Инструмент | Зачем |
|------------|--------|
| [Git](https://git-scm.com) | обязателен. При установке на Windows оставьте «Git from the command line» |
| Браузер + github.com | создать репо, issues, приглашение |
| [GitHub Desktop](https://desktop.github.com) | коммиты кнопками, если терминал пока сложен |
| Cursor / VS Code | правки файлов; слева значок Source Control = тот же Git |
| GitHub CLI `gh` | необязательно; преподаватель им пользуется, вам на ЛР0 не нужен |

Проверка Git в PowerShell: `git --version`. Если команда не находится — Git не в PATH, переустановите и откройте терминал заново.

### Команды, которых достаточно на семестр

```powershell
git status
git add <файл>
git commit -m "сообщение"
git push
git pull
git log --oneline
git clone https://github.com/ВАШ-ЛОГИН/ris-web-2026.git
git remote -v
```

Реже, но полезно:

```powershell
git diff                  # что изменилось до коммита
git restore <файл>        # отменить правки в файле (осторожно)
git branch                # список веток; на курсе живёте в main
```

Ветки, pull request и fork на этом курсе **не обязательны**. Один `main`, коммиты, push.

### Что смотреть на сайте GitHub

| Раздел | Зачем вам |
|--------|-----------|
| **Code** | файлы текущей версии |
| **Commits** (история) | виден ли последний push |
| **Issues** | замечания преподавателя |
| **Settings → Collaborators** | есть ли `martitrofan` |
| **Settings → Danger Zone** | приватность |

## 8. Бесплатные альтернативы GitHub

Контроль версий — это Git. Сайт-хостинг можно выбрать другой. На курсе **предпочтителен GitHub**: туда смотрит таблица сдачи и туда пишут issue.

| Где | Бесплатно для учёбы | На курсе |
|-----|---------------------|----------|
| **GitHub** | да; приватные репозитории есть | **основной вариант** |
| **GitLab.com** | да; приватные есть | принимаем, если пригласите преподавателя |
| **Codeberg** | да, на Forgejo | только по согласованию (проверять неудобно) |
| **Bitbucket** | да, с лимитами | не используем |
| **Gitea / свой сервер** | да | не используем |
| Яндекс Диск, Google Drive, почта, Telegram | это **не** СКВ | **не принимаем** |

Если GitHub из сети вуза не открывается — GitLab.com. Ссылку всё равно положите в форму, в комментарии укажите, что это GitLab, и пригласите преподавателя.

Не путайте: «я залил zip на Диск» ≠ репозиторий. Нет истории коммитов и нет issue.
