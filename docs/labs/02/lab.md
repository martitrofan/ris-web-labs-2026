## Зачем эта работа

В ЛР1 вы написали, *что* система делает. Сегодня рисуете, *из чего она состоит* и *какими просьбами* браузер будет разговаривать с сервером. Кода всё ещё нет. Если имена придумать сейчас и потом поменять — придётся переписывать и Vue, и C#, и SQL. Поэтому сегодняшние слова = слова на весь семестр.

## Теория на пару

40–50 минут, если лекций не было.

### 1. Кто кого спрашивает

В браузере человек видит таблицу. Браузер сам **не** лезет в PostgreSQL. Он посылает просьбу программе на сервере. Сервер смотрит правила и отвечает. Если два человека открыли страницу, они видят одно и то же только потому, что правда лежит на сервере, а не в голове каждого браузера.

Это как столовая: вы не идёте на кухню в кастрюлю. Вы говорите кассиру. Кассир решает, можно ли, и отдаёт тарелку.

Три узла на схеме (порты запомнить):

| Кто | Порт | Что делает |
|-----|------|------------|
| Vue-клиент (потом, ЛР3) | 5173 | Рисует экраны, шлёт просьбы |
| ASP.NET Core | 5000 | Правила, ответы |
| PostgreSQL | обычно 5432 | Хранит строки |

Стрелки только: клиент → сервер, сервер → база. Стрелки «браузер → PostgreSQL» на сдаче быть не должно.

**Подпись к схеме (обязательна в `/docs`):** «Это и есть архитектура web-ИС семестра» — три узла, две связи, один источник правды о заявках. Не микросервисы и не «сайт на одном файле». На текущем контроле (ТК) 1 и на защите курсовой показывают именно эту картинку и объясняют, почему браузер не пишет в базу напрямую.

Критерии качества учебного web (тема 1.5, разбор на лекции 04): воспроизводимый запуск по README; один машинный `id` (отдельно от человеческого `number`); понятная граница MVP; имя справочника не копируют в каждую заявку (3НФ).

### 2. HTTP простыми словами

HTTP — правила разговора браузера и сервера. На курсе смотрим четыре части, как в письме: глагол, адрес, текст письма, штамп ответа.

| Часть | Вопрос | Примеры |
|-------|--------|---------|
| Метод | Что сделать? | `GET` — прочитать, `POST` — создать новое, `PATCH` — подправить кусок |
| Путь | К чему? | `/api/tickets` — все заявки, `/api/tickets/17` — одна |
| Тело | Что приложить? | Текст в формате JSON: `{ "title": "Насос встал" }` |
| Код | Чем кончилось? | `201` создали, `200` ок, `400` прислали ерунду, `404` такой записи нет, `409` так нельзя по правилам |

JSON — текст с фигурными скобками, его понимают и Vue, и C#. Не путать с таблицей Excel.

Адрес сервера в разработке: `http://localhost:5000`. Слово `localhost` значит «этот компьютер».

### 3. Сущность, ключ, связь

**Сущность** — то, о чём хранят отдельную строку. На курсе минимум три:

1. главный объект (заявка, бронь, обращение);
2. справочник рядом (участок, аудитория, группа) — иначе не будет соединения таблиц;
3. пользователь (кто создал, кого назначили).

**Первичный ключ (PK)** — технический `id`, обычно число. Его ставят в адрес: `/api/tickets/17`. Человеку его диктовать неудобно.

**Человеческий номер** (`number`) — «заявка 104», «бронь А-12». Это другое поле. Фамилия «Иванов» ключом не бывает: однофамильцы, опечатки, смена фамилии.

**Внешний ключ (FK)** — ссылка числом на другую таблицу. В заявке пишут `siteId: 3`, а название «Котельная Б» лежит в таблице участков у строки с `id = 3`.

**Третья нормальная форма (3НФ)** на этом курсе одной бытовой фразой: *название участка хранят один раз, у участка. В заявке только номер участка.* Если в каждой заявке написано «Котельная Б» текстом, переименование правят в десятках строк и где-то забудут.

Связи подписывают словами, не только ромбиками:

- один участок — много заявок;
- один человек создал много заявок;
- у заявки ноль или один исполнитель (сразу после создания исполнителя ещё нет).

### 4. Статусы и почему два PATCH

В JSON и в базе только четыре английских кода: `New`, `InProgress`, `Closed`, `Cancelled`. На экране можно «Новая», «В работе».

`PATCH` значит «подправить часть». Назначение исполнителя — один адрес (`…/assignee`). Смена статуса — другой (`…/status`). Если сделать один «обновить заявку целиком», инженер случайно сменит и исполнителя, и тему. Правила из ЛР1 тогда не проверить.

Удаление (`DELETE`) не планировать. Отмена — это статус `Cancelled`, строка остаётся.

Путь вида `/api/tickets/create` не использовать. Действие несёт метод (`POST`), не слово «create» в адресе.

Имена в таблице API сегодня = имена в коде весь семестр. Свои слова — через таблицу соответствия из ЛР1.

## Пример куска таблицы API

Подставьте свой путь вместо `tickets`.

| Метод и путь | Что прислать | Успех | Ошибка |
|--------------|--------------|-------|--------|
| `POST /api/tickets` | title, siteId, description | 201, в ответе id, number, status New | 400 |
| `GET /api/tickets` | ничего | 200, список (пустой список — тоже 200 и `[]`) | — |
| `GET /api/tickets/{id}` | ничего | 200 | 404 |
| `PATCH /api/tickets/{id}/assignee` | assigneeUserId | 200 | 404 |
| `PATCH /api/tickets/{id}/status` | status | 200 | 404 или 409 |

Пример тела создания:

```json
{
  "title": "Насос участка Б не запускается",
  "siteId": 2,
  "description": "После грозы гудит и встаёт через минуту"
}
```

`id` и `status` клиент **не** присылает. Их поставит сервер.

## Пример матрицы

| Требование ЛР1 | Поле или сущность | Запрос | Критерий |
|----------------|-------------------|--------|----------|
| Диспетчер создаёт заявку | Ticket, title, siteId | POST /api/tickets | Критерий 1 |
| Диспетчер назначает инженера | assigneeUserId | PATCH …/assignee | Критерий 2 |
| Инженер берёт в работу | status | PATCH …/status | Критерий 3 |

Если на требование нет строки — модель не готова, не «потом придумаем».

## Порядок на 4 часа

1. Открыть три критерия ЛР1 и таблицу соответствия.
2. На листе или в файле выписать сущности и поля. Справочник и пользователь — отдельные прямоугольники.
3. Нарисовать ER, подписать PK, FK и фразы связей.
4. Проверить 3НФ: нет ли «название участка» внутри заявки.
5. Четыре статуса и стрелки переходов (кто имеет право).
6. Заполнить таблицу API. Удаление не писать.
7. Матрица на все три критерия.
8. Схема: три прямоугольника, две стрелки, один пример запроса целиком (метод, путь, тело, код). Подпись: «это и есть архитектура web-ИС семестра».
9. Коммит в **тот же** репозиторий.

## Сдача

У каждой сущности есть ключ. Три требования ЛР1 имеют строку в матрице. На схеме нет стрелки из браузера в базу; есть подпись про архитектуру web-ИС семестра. На защите своими словами: почему участок не строка в заявке; какой запрос закрывает критерий 2; чем `id` не номер «104»; что значит «воспроизводимый запуск» для вашей схемы.

## Частые ошибки

- Одна сущность «заявка» со столбцом «имя инженера» текстом — нет пользователя как сущности.
- На схеме браузер соединён с PostgreSQL.
- В API один путь `POST /update` на всё.
- Пустой список хотят отдать кодом 404. 404 — нет *конкретного* id. Пустой список — нормальный `200` и `[]`.
