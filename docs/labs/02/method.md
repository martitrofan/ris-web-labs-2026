## 3. Коротко по делу

### 3.1. Три узла

Клиент Vue рисует экран и отправляет HTTP-запросы. ASP.NET Core проверяет правила. PostgreSQL хранит данные.

```text
Vue 3 + Vite             ASP.NET Core              PostgreSQL
localhost:5173  ───────► localhost:5000  ───────► обычно :5432
                  HTTP                    запросы к БД
```

Под схемой дословно напишите:

> архитектура web-ИС семестра

Прямой стрелки от браузера к базе нет: иначе клиент получает доступ к данным и обходит серверные правила.

### 3.2. Ключи и 3НФ

- `id` — машинный первичный ключ (PK).
- `number` — человеческий номер записи, не замена `id`.
- `siteId` — внешний ключ (FK) на справочник.
- `assigneeUserId` — внешний ключ на пользователя; при создании может быть пустым.

Проверка 3НФ для курса: название участка хранится один раз в таблице участков. В заявке хранится только `siteId`.

### 3.3. API и два PATCH

Назначение исполнителя и смена статуса — разные действия:

```text
PATCH /api/tickets/{id}/assignee
PATCH /api/tickets/{id}/status
```

Статусы только: `New`, `InProgress`, `Closed`, `Cancelled`. Отмена — `Cancelled`, а не удаление строки.

### Шаг A. Зафиксируйте словарь проекта

В начале `data-model.md` напишите соответствия:

### Шаг B–C. Сделайте ER-модель

Для главного объекта предусмотрите минимум:

```text
id, number, title, description, status,
siteId, createdByUserId, assigneeUserId
```

У справочника: `id`, `name`. У пользователя: `id`, имя или логин. Подпишите:

- один справочник — много главных объектов;
- один пользователь создаёт много объектов;
- один пользователь может быть назначен на много объектов;
- у нового объекта исполнитель может отсутствовать.

### Шаг D. Запишите проверку 3НФ

Добавьте в `data-model.md` короткий ответ:

> Название справочника хранится в сущности Site один раз. Ticket содержит внешний ключ siteId. При переименовании участка меняется одна строка, поэтому текст названия не дублируется в заявках.

Замените слова на свою тему, смысл сохраните.

### Шаг E. Заполните API

Минимальная таблица:

| Метод и путь | Тело | Успех | Возможная ошибка |
|--------------|------|-------|------------------|
| `GET /api/tickets` | — | `200`, массив или `[]` | — |
| `GET /api/tickets/{id}` | — | `200`, объект | `404` |
| `POST /api/tickets` | `title`, `siteId`, `description` | `201`, `id`, `number`, `status: New` | `400` |
| `PATCH /api/tickets/{id}/assignee` | `assigneeUserId` | `200` | `404` |
| `PATCH /api/tickets/{id}/status` | `status` | `200` | `404`, `409` |

Клиент не присылает при создании `id`, `number`, `status` и исполнителя. Их определяет сервер.

### Шаг F. Сделайте матрицу

| Требование ЛР1 | Поле или сущность | Запрос | Критерий |
|----------------|-------------------|--------|----------|
| Создать объект | `Ticket`, `title`, `siteId`, `description` | `POST /api/tickets` | 1 |
| Назначить исполнителя | `assigneeUserId` | `PATCH …/assignee` | 2 |
| Перевести в работу | `status` | `PATCH …/status` | 3 |

Если строку нельзя заполнить, вернитесь к ТЗ или модели: договор пока противоречив.

### Шаг G. Проверьте архитектурную схему

На схеме должны быть:

1. Vue 3, порт `5173`.
2. ASP.NET Core, порт `5000`.
3. PostgreSQL, обычно порт `5432`.
4. Стрелка Vue → API с примером `POST /api/tickets`.
5. Стрелка API → БД.
6. Подпись «архитектура web-ИС семестра».

## 5. Частые косяки

| Ошибка | Как исправить |
|--------|---------------|
| `siteName` хранится в каждой заявке | вынести Site, оставить `siteId` |
| Фамилия пользователя используется как PK | добавить числовой `id` |
| `id` и `number` считаются одним полем | оставить оба с разным назначением |
| Пустой список возвращает `404` | вернуть `200` и `[]` |
| Один PATCH меняет всё | разделить `/assignee` и `/status` |
| В API есть DELETE | убрать; отмена = `Cancelled` |
| Браузер связан с БД | удалить прямую стрелку |
| Нарисованы сущности без связи с ЛР1 | заполнить матрицу для трёх критериев |
