## Теория на пару

### Зачем PostgreSQL, если есть список в C#

Список в памяти — бумажка на столе. Выключили свет (процесс) — бумажки нет. PostgreSQL пишет на диск. Завтра утром заявки на месте.

SQL — язык разговора с базой. Не C# и не JavaScript. Предложения вроде «возьми из таблицы заявок те, что в работе, и подпиши имя участка».

| Команда | Смысл |
|---------|--------|
| `CREATE TABLE` | Завести таблицу (графы тетради) |
| `INSERT` | Вписать строку |
| `SELECT` | Прочитать |
| `JOIN` | Посмотреть сразу две таблицы: заявка + название участка |
| `GROUP BY` | Сгруппировать: сколько заявок в каждом статусе |
| `CREATE INDEX` | Оглавление: быстрее искать по частому полю |

Как читать SELECT вслух: *откуда* → *с чем склеить* → *какое условие* → *как упорядочить или сгруппировать* → *какие столбцы показать*.

### Ключи без учебника по базам

**Первичный ключ** — уникальный номер строки. Двух заявок с одним `id` не будет.

**Внешний ключ** — «эта заявка ссылается на участок 3». Если участка 3 нет, база откажется принять строку. Это лучше, чем потом гадать, куда делся участок.

**CHECK** — «статус только из четырёх слов». Нельзя записать `Done` или `новая`.

**3НФ как в ЛР2:** столбец «название участка» в таблице заявок не заводите. Только `site_id`.

Столбцы заявки в примере курса (свои имена — из ЛР2, смысл тот же):

`id`, `number`, `title`, `description`, `site_id`, `status`, `created_at` (тип `timestamptz` — момент с часовым поясом), `created_by_user_id`, `assignee_user_id`.

У новой заявки исполнитель пустой: в SQL это `NULL` (нет значения), не ноль и не пустая строка.

Приоритет не добавлять.

### Индекс

Как закладка в толстой книге. Ищете часто «все New» — закладка по `status` помогает. Ищете редко по описанию — индекс не нужен: он занимает место и чуть тормозит каждую новую вставку.

Два индекса обязательны: статус и внешний ключ справочника. По дате — по желанию.

`DELETE FROM tickets WHERE …` вычёркивает строки, тетрадь остаётся. `DROP TABLE tickets` выбрасывает всю тетрадь. `DROP` в учебном скрипте допустим только чтобы пересоздать схему с нуля, не как «рабочая команда приложения».

## Пример куска схемы (сокращённо)

```sql
CREATE TABLE sites (
  id    integer PRIMARY KEY,
  name  text NOT NULL
);

CREATE TABLE tickets (
  id                   integer PRIMARY KEY,
  number               text NOT NULL UNIQUE,
  title                text NOT NULL,
  site_id              integer NOT NULL REFERENCES sites (id),
  status               text NOT NULL CHECK (status IN ('New', 'InProgress', 'Closed', 'Cancelled')),
  assignee_user_id     integer NULL
);

CREATE INDEX tickets_status_idx ON tickets (status);
```

Это каркас, не полный файл. Добавьте пользователей, описание, даты — как в ЛР2.

Пример соединения и подсчёта:

```sql
SELECT tickets.number, sites.name, tickets.status
FROM tickets
JOIN sites ON sites.id = tickets.site_id
WHERE tickets.status = 'New'
ORDER BY tickets.created_at DESC;

SELECT status, COUNT(*) AS cnt
FROM tickets
GROUP BY status;
```

## Сдача

Скрипт схемы повторяется. Есть внешний ключ и CHECK. JOIN показывает имя, не только число. GROUP BY понятен роли «руководитель» из ЛР1. На защите: зачем индекс по статусу; почему имя участка не текст в заявке; чем JOIN не GROUP BY.

## Частые ошибки

- Одна таблица «всё сразу» без участков.
- Статус без CHECK — в базе живёт `new`, `NEW` и `Новая`.
- Пароль `postgres` в README и в Git.
- Сдали скрин EF вместо `queries.sql`.
- `JOIN` написали, но выбрали только `site_id`, имя участка так и не появилось.
- В `seed` только статус `New` — GROUP BY на защите нечего показать.
- Столбцы `siteId` в SQL (camelCase) — в PostgreSQL обычно `site_id`; иначе ЛР10 разъедется.
