```text

├── README.md

└── docs/
    ├── project-proposal.md      ← заявка на тему
    └── lab-01-requirements.md   ← техническое задание
```

Папок `frontend/`, `backend/`, `db/` пока нет — их заведёте позже **в этом же** репозитории.

В терминале:

```bash
git init
git add README.md docs
git commit -m "ЛР1: заявка на тему и требования"
```

Проверка: `git log --oneline` показывает хотя бы один коммит, в `docs/` два файла.

В `README.md` минимум: название темы (или «запас»), ФИО, группа, стек (Vue 3 + ASP.NET Core + PostgreSQL — код позже), статус темы.

**Не кладите** в репозиторий: чужой zip «как образец», тринадцать репозиториев «на каждую лабу», пустые файлы «потом заполню».

## Выбор темы — самое важное сегодня

### Как устроен курс у всех

Схема одна, слова разные:

1. Кто-то **создаёт** главную запись (обращение, бронь, заявка…).
2. Кто-то **назначает** исполнителя.
3. Исполнитель **меняет статус** только своей записи.
4. Потом это станет Vue + ASP.NET Core + PostgreSQL.

На лекциях часто говорят про заявки энергопредприятия. Повторять этот пример в коде **не обязаны**. Это запас, если к 14.09 свою тему не утвердили.

### Двенадцать проверок — все должны быть «да»

Один «нет» — тему правят или дописывают. Лабораторные из‑за этого не выкидывают.

| № | Вопрос | да/нет |
|---|--------|--------|
| 1 | Есть процесс со сменой состояния, а не витрина / лендинг / каталог? | |
| 2 | Одна главная сущность, не «весь вуз сразу»? | |
| 3 | Есть справочник и ссылка на него **числом** (участок, аудитория, комната…)? | |
| 4 | Минимум две роли с **разным** правом (кто создаёт ≠ кто исполняет)? | |
| 5 | Назначение исполнителя и смена статуса — **разные** действия? | |
| 6 | Четыре статуса в API и БД: `New`, `InProgress`, `Closed`, `Cancelled`? | |
| 7 | Будут и машинный `id`, и человеческий номер (`number`)? | |
| 8 | При создании три поля: заголовок, ссылка на справочник, описание? | |
| 9 | Три экрана (список, создание, вход) и стек Vue + ASP.NET Core + PostgreSQL? | |
| 10 | В семестре только учебный минимум, не весь диплом? | |
| 11 | В заявке записан запас под ВКР (не меньше 4 пунктов с разных «полок»)? | |
| 12 | Тема не копия соседа без отличия (другой заказчик / объект / роли)? | |

Коротко по смыслу:

- Нужен объект, у которого через неделю можно сказать: в каком он состоянии и кто за него отвечает.
- «Информационная система университета» со складом, кадрами и ремонтом сразу — не собрать. Одну главную сущность.
- Название участка / аудитории лежит в справочнике один раз; в заявке только число `siteId` (или ваше имя поля).
- Кто создаёт — не тот, кто исполняет. Иначе потом нечего запрещать.
- Сначала назначили Иванова, потом Иванов перевёл статус. Не одна кнопка «сохранить всё».
- Коды статусов английские, как написано. Подписи на экране — ваши слова.
- React, Laravel, Firebase, Django вместо стека курса — тему не утвердят.

### Что писать в заявке

Скопируйте шаблон [project-proposal.md](templates/project-proposal.md) в свой репозиторий как `docs/project-proposal.md` и заполните:

1. Название и организация (конкретная, не «некая фирма»).
2. Главная сущность и справочник.
3. Роли и права (таблица да/нет).
4. Сценарий в одно предложение.
5. Таблица соответствия курсу (ваши слова рядом со словами лекции).
6. Что не входит в семестр.
7. Запас под ВКР — не меньше 4 пунктов с разных полок: данные/процесс, связь с другими системами, масштаб. Не «улучшить дизайн» и не «переписать на React».
8. Чем не копия соседа.
9. Самопроверка по 12 пунктам.

Преподаватель в том же файле ставит: **утверждено** / **доработать** / **отказ**.

Пример нормального запаса под диплом (для заявок на ремонт): привязать конкретный насос и наряд-допуск; считать, сколько часов заявка висит; выгрузить сводку начальнику; забирать простой из журнала обходов. Для своей темы — так же конкретно.

## Как заполнить ТЗ

Скопируйте [lab-01-requirements.md](templates/lab-01-requirements.md) → `docs/lab-01-requirements.md` в своём репозитории.  
Пустые «…» к сдаче не оставляйте.

| Раздел | Минимум |
|--------|---------|
| Предметная область | кто заказчик, какой процесс |
| Как есть | 8–12 предложений, где теряется факт |
| Как будет | одна запись в системе |
| Граница | что внутри семестра / что снаружи |
| Роли | таблица да/нет, минимум 2 роли |
| Таблица соответствия курсу | все строки заполнены |
| Функциональные требования | 8–15 строк: роль + действие + что видно |
| Нефункциональные | 3–5 строк; одно про данные после перезапуска сервера |
| Use case | **один** целиком: актёр, поток, альтернатива, постусловие |
| Три критерия | создать / назначить / в работу — Дано / Когда / Тогда |

### Четыре статуса

| Код в API и БД | Смысл | Подпись на экране |
|----------------|--------|-------------------|
| `New` | только создали | своя (Новая / Поступила…) |
| `InProgress` | исполнитель взял | своя |
| `Closed` | сделали | своя |
| `Cancelled` | отменили | своя |

### Три критерия — образец

Подставьте свои роли и слова.

**1. Создать**  
**Дано:** … вошёл.  
**Когда:** заполняет заголовок (5–80), справочник числом (> 0), описание (10–500), жмёт «Создать».  
**Тогда:** запись со статусом `New` и человеческим номером. Да/нет.

**2. Назначить**  
**Дано:** … и запись `New`.  
**Когда:** назначает исполнителя **отдельным** действием.  
**Тогда:** исполнитель записан; статус можно ещё не менять. Да/нет.

**3. В работу**  
**Дано:** назначенный исполнитель вошёл.  
**Когда:** переводит свою запись `New` → `InProgress`.  
**Тогда:** статус «в работе»; чужой логин эту запись не двигает. Да/нет.

### Частые косяки в ТЗ

| Ошибка | Как правильно |
|--------|----------------|
| «Можно создавать заявки» без роли | Кто именно может |
| «Удобный интерфейс» | Число или проверяемый факт |
| Один статус «открыта/закрыта» | Четыре кода курса |
| «Редактировать» = и назначение, и статус | Два разных требования |
| Нет use case, только короткая история | Добавить use case целиком |
| Нет запрета | Хотя бы «исполнитель не создаёт» / «не чужое» |

## Чеклист перед «готово»

**Репозиторий**

- [ ] Один репозиторий, не тринадцать
- [ ] `README.md` с ФИО, группой, темой или запасом
- [ ] `docs/project-proposal.md` и `docs/lab-01-requirements.md`
- [ ] Хотя бы один `git commit`
- [ ] Нет чужого проекта и секретов

**Тема**

- [ ] В заявке заполнены все разделы шаблона
- [ ] 12 пунктов — все «да» (или согласован запас)
- [ ] Преподаватель видел заявку

**ТЗ**

- [ ] Роли с разным правом
- [ ] 8–15 функциональных и 3–5 нефункциональных требований
- [ ] Один use case целиком
- [ ] Три критерия Дано / Когда / Тогда
- [ ] Таблица соответствия курсу заполнена
- [ ] Назначение и статус не слиты в одно требование

**Устно на защите (подготовьте)**

1. Зачем такая граница системы?
2. Как проверить одно нефункциональное требование?
3. Какие три критерия обязательны до курсовой?
4. Чем тема не копия соседа?
