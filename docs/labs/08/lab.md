## Зачем эта работа

Каркас из ЛР7 умеет сказать «я жив». Сегодня он умеет принять заявку, отдать список, назначить человека и сменить статус. Данные всё ещё в памяти: перезапустили сервер — список пуст. Это снова нормально и пишется в README.

ТК3 смотрят три вещи: успешное создание, отказ на короткую тему (`400`), запрос несуществующего id (`404`). Назначение и 409 желательны сегодня, иначе на ЛР11 придётся доделывать в спешке.

## Цель

Предсказуемые адреса и коды. Свои пути — из таблицы ЛР2.

## Что сдать

Пример курса. У вас вместо `tickets` своё слово.

| Просьба | Зачем человеку |
|---------|----------------|
| `POST /api/tickets` | Создать |
| `GET /api/tickets` | Список |
| `GET /api/tickets/{id}` | Одна карточка |
| `PATCH /api/tickets/{id}/assignee` | Назначить исполнителя |
| `PATCH /api/tickets/{id}/status` | Сменить статус |

Один общий «обновить всю заявку» не обязателен. Удаление не делать.

| Код | Когда |
|-----|--------|
| 200 | Прочитали список или одну запись. Пустой список — тоже 200 и `[]`, не 404 |
| 201 | Только что создали. В теле: `id`, `number`, `status: "New"` |
| 400 | Прислали плохое тело: короткая тема, не число, пустое описание |
| 404 | В адресе id, которого нет |
| 409 | Правила процесса: нельзя «в работу» без исполнителя или чужой |

`204` не нужен: мы ничего не удаляем. Ошибки одним видом JSON, достаточно стандартного `ProblemDetails` (у ASP.NET он часто уже есть).

Дополнительно к таблице API в репозиторий кладут:

| Артефакт | Куда | Зачем (РПД 3.3 / 3.4) |
|----------|------|------------------------|
| Коллекция запросов | `/docs/api-collection/` — экспорт Swagger или JSON Postman/Insomnia | повторить успех, 400, 404 без «тыканья по памяти» |
| Доказательство лога | скрин или фрагмент консоли/файла лога в отчёте | неожиданный сбой записан на сервере, клиенту стек не отдали |

Заготовка коллекции: [api-collection-postman.json](/labs/08/templates/api-collection-postman) — импортировать и поправить путь под свою тему.

## Теория на пару

45 минут.

### REST без учебника

Думайте о **вещах**, не о командах. Вещь — заявка. Папка всех заявок — `/api/tickets`. Одна заявка — `/api/tickets/17`.

Глагол HTTP говорит, что сделать с вещью. Не делайте адрес `/api/tickets/create` — слово «create» уже есть в глаголе `POST`.

Повторный `GET /api/tickets/17` не создаёт вторую заявку. Повторный `POST` — может создать вторую. Поэтому создание — всегда `POST`.

### DTO — «формочка на входе», не таблица

**DTO** (data transfer object) — какие поля можно прислать или забрать по сети. **Сущность** — что вы храните в памяти (потом в базе).

На создание клиент присылает только то, что человек заполняет: тему, участок, описание. Не присылает `id`, `status`, время создания. Иначе хитрый клиент поставит себе статус `Closed` сразу.

Проверку длины удобно повесить на DTO. Если контроллер помечен `[ApiController]`, плохая формочка сама станет 400.

Правило «нельзя взять в работу, пока нет исполнителя» — не про длину строки. Его пишут в **сервисе**, ответ **409**.

Контроллер: принял JSON, вызвал сервис, вернул код. Не копируйте таблицу переходов статусов в каждый метод.

### Кто сейчас «пользователь»

Настоящий вход — ЛР11. Сегодня хватит заголовка `X-User-Id: 2` или поля в теле. Выберите **один** способ и напишите в README. Код 403 пока не вводить: чужой переход тоже отдайте как 409. Иначе на защите смешают 403 и 409.

### Числа, которые все забывают

Тема 5–80, описание 10–500, `siteId` целое > 0. Другие границы — только если в ЛР1 так написали.

### Коллекция запросов (обязательно)

В отчёте и в Git должен лежать **набор**, которым сосед повторит ТК3 без вашей помощи:

1. `POST` создание — ожидание **201**, в теле `id`, `number`, `status: New`.
2. `POST` с короткой темой — **400** (не 500).
3. `GET` несуществующего id — **404**.
4. Желательно: `PATCH …/status` без исполнителя — **409**.

Форматы (любой один):

- экспорт из Swagger UI / OpenAPI, если умеете сохранить примеры; **или**
- JSON Postman / Insomnia в `/docs/api-collection/tickets.postman_collection.json` (имя своё).

В README одна строка: как импортировать коллекцию и какой базовый URL (`http://localhost:5000`).

### Лог на неожиданный сбой (обязательно)

Ожидаемые отказы (400 / 404 / 409) — это **не** авария: их отдаёте клиенту через `ProblemDetails`, в лог можно писать кратко.

Неожиданное исключение (нулевой сервис, баг в коде):

1. На сервере — **одна** понятная строка лога: операция + `ticketId` (если есть) + тип ошибки.
2. Клиенту — безопасный `500` / `ProblemDetails` **без** stack trace и путей к файлам на диске.
3. В отчёте — скрин этой строки лога (консоль `dotnet run` или настроенный провайдер).

Пример идеи (имена свои):

```csharp
_logger.LogError(ex, "CreateTicket failed for SiteId {SiteId}", dto.SiteId);
return Problem(statusCode: 500, title: "Не удалось обработать запрос");
```

Нельзя: `return Content(ex.ToString())`, полный JSON с паролем, весь request body «на всякий случай». Подробнее — лекция 13.

Как вызвать учебный сбой для скрина: временно бросить исключение в сервисе после успешной валидации, снять лог, убрать бросок перед коммитом **или** оставить переключаемый флаг Development-only и описать в README.

## Пример тел

Создание, клиент шлёт:

```json
{
  "title": "Насос участка Б не запускается",
  "siteId": 2,
  "description": "После грозы гудит и встаёт через минуту"
}
```

Сервер отвечает 201:

```json
{
  "id": 17,
  "number": "A-117",
  "title": "Насос участка Б не запускается",
  "siteId": 2,
  "description": "После грозы гудит и встаёт через минуту",
  "status": "New",
  "assigneeUserId": null
}
```

Назначение:

```json
{ "assigneeUserId": 5 }
```

Статус:

```json
{ "status": "InProgress" }
```

В работу — только если `assigneeUserId` уже стоит и совпадает с тем, кто вызывает.

## Порядок на 4 часа

1. Два DTO: вход создания и ответ (можно один ответ на всё чтение).
2. В сервисе список в памяти и счётчик id.
3. POST и оба GET. Проверить пустой список — 200 и `[]`.
4. Проверка полей → 400.
5. Два PATCH. Запрещённый переход → 409.
6. Выдуманный id → 404, не «жёлтый экран» 500.
7. Одна ветка неожиданного сбоя → строка в логе, клиенту без стека.
8. Сохранить коллекцию запросов (201, 400, 404, лучше 409) в `/docs/api-collection/`.
9. README: порт, как открыть Swagger, как импортировать коллекцию, данные в памяти.

## Сдача

201 и статус `New`. Короткий title не создаёт строку. Нет id — 404. В репозитории — коллекция и доказательство лога. На защите: зачем два PATCH; что в теле при 400; чем DTO не строка таблицы; что видит клиент при 500 и что видит разработчик в логе.

## Частые ошибки

- Клиент при создании шлёт `"status": "Closed"` и сервер слушается.
- Пустой список отдают 404.
- Нет id — 500, потому что забыли `if (item == null)`.
- Один метод `Update(Ticket t)` меняет и исполнителя, и статус.
- Путь `/api/createTicket`.
- Коллекцию «сделали в Swagger руками», в Git ничего нет — сосед не повторит.
- Клиенту отдали stack trace «чтобы было понятнее».
- Логируют весь входящий JSON с будущим токеном.
