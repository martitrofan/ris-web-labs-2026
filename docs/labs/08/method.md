## Зачем вы здесь

На сервере появляются настоящие маршруты главного объекта: список, одна запись, создание, отдельно назначение исполнителя, отдельно смена статуса.

PostgreSQL ещё нет — всё в памяти, после перезапуска пропадёт. Зато ответы должны быть предсказуемыми: `201`, `400`, `404`, `409`. Сосед без ваших подсказок гоняет запросы из коллекции.

Имена вроде `tickets` заменяйте словами своей темы из документов в `/docs`.

## 1. Цель одной фразой

REST главного объекта: создать, прочитать, отдельно назначить, отдельно сменить статус. Ответы `201` / `400` / `404` / `409`. Ошибки на сервере логируются без stack trace клиенту.

### 2.2. Маршруты

| Метод и путь | Успех | Назначение |
|---|---:|---|
| `POST /api/tickets` | 201 | создать запись |
| `GET /api/tickets` | 200 | получить список, включая `[]` |
| `GET /api/tickets/{id}` | 200 | получить одну запись |
| `PATCH /api/tickets/{id}/assignee` | 200 | назначить исполнителя |
| `PATCH /api/tickets/{id}/status` | 200 | изменить статус |

`DELETE` в курсе не делаем. Общий PATCH «изменить всё» не заменяет два PATCH.

### 2.3. Коды отказов

| Код | Когда вернуть |
|---:|---|
| 400 | JSON или поля не прошли проверку |
| 404 | записи с таким `id` нет |
| 409 | действие противоречит состоянию процесса |
| 500 | неожиданный сбой; клиенту только безопасное сообщение |

## 3. Контракт данных

### 3.1. Создание

Клиент присылает только изменяемые человеком поля:

```json
{
  "title": "Насос участка Б не запускается",
  "siteId": 2,
  "description": "После грозы гудит и останавливается"
}
```

Сервер сам задаёт `id`, `number`, `status: "New"` и пустого исполнителя.

Минимальные проверки:

- `title`: 5–80 символов;
- `description`: 10–500 символов;
- `siteId`: целое число больше нуля.

### 3.2. Два PATCH

Назначение:

```json
{ "assigneeUserId": 5 }
```

Смена статуса:

```json
{ "status": "InProgress" }
```

Допустимые статусы: `New`, `InProgress`, `Closed`, `Cancelled`.
Нельзя переводить запись в `InProgress`, пока исполнитель не назначен.
Такой отказ — `409`, а не `400`.

## 5. Проверка по шагам

### 5.1. Запуск

```bash
cd backend
dotnet run
```

Используйте базовый адрес `http://localhost:5000`.
Если ASP.NET выбрал другой порт, настройте профиль или исправьте README и коллекцию.

### 5.2. Обязательные запросы коллекции

1. Успешный `POST`: ожидание `201`, есть `id`, `number`, `New`.
2. `POST` с title из трёх символов: ожидание `400`.
3. `GET /999999`: ожидание `404`.
4. `PATCH .../status` без исполнителя: ожидание `409`.
5. Оба PATCH после назначения: ожидание успешного ответа.

Сохраните экспорт в `/docs/api-collection/`.
Можно начать с [шаблона коллекции](/labs/08/templates/api-collection-postman).

### 5.3. Лог неожиданной ошибки

Временно вызовите учебное исключение после успешной валидации.
На сервере должна появиться одна понятная строка:

```text
CreateTicket failed; siteId=2; error=InvalidOperationException
```

Клиент получает безопасный `ProblemDetails` без:

- stack trace;
- абсолютных путей;
- тела запроса целиком;
- токенов и секретов.

Уберите искусственный сбой перед коммитом.
Скрин строки лога положите в отчёт.

## 6. Частые ошибки

| Ошибка | Как исправить |
|---|---|
| Клиент задаёт `status: Closed` при POST | убрать status из входного DTO |
| Пустой список возвращает 404 | вернуть 200 и `[]` |
| Неизвестный id приводит к 500 | проверить результат поиска и вернуть 404 |
| Один PATCH меняет всё | разделить `/assignee` и `/status` |
| Запрещённый переход даёт 400 | вернуть 409 |
| Коллекция осталась только в Postman | экспортировать JSON в Git |
| Клиент видит `ex.ToString()` | вернуть безопасный ProblemDetails |
| В лог попадает весь JSON | оставить операцию, id и тип ошибки |
| Данные исчезли после рестарта | для ЛР8 это нормально; написать в README |
